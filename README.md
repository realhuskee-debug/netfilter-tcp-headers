# Netfilter TCP Processing Lab

## Описание проекта

Репозиторий содержит материалы лабораторного исследования, посвященного анализу влияния дополнительной обработки TCP-пакетов в ядре Linux на пропускную способность сетевого канала. В основе стенда используется загружаемый модуль ядра `nf_tcp_lab`, подключаемый к подсистеме Netfilter через хук `NF_INET_POST_ROUTING`. Модуль позволяет перехватывать исходящие TCP-сегменты, собирать статистику обработки и, при необходимости, включать режим активной дополнительной обработки заголовка, моделирующий рост вычислительных накладных расходов.

## Лабораторный стенд

Стенд состоит из двух узлов под управлением Linux, соединенных в изолированной сети.

Первый узел выполняет роль клиента и используется для генерации TCP-трафика, загрузки модуля ядра и сбора статистики. Второй узел выполняет роль сервера `iperf3` и принимает тестовый трафик.

В рамках статьи исследуются три режима работы:

- базовый режим без загрузки модуля;
- режим пассивного перехвата пакетов без дополнительной обработки;
- режим активной дополнительной обработки TCP-пакетов с параметром `transform_level`.

## Состав проекта

- `nf_tcp_lab.c` — исходный код исследовательского модуля ядра Linux;
- `Makefile` — файл сборки модуля через `kbuild`;
- `run_server.sh` — запуск `iperf3` в серверном режиме;
- `run_client_baseline.sh` — серия эталонных измерений без загрузки модуля;
- `run_client_hook.sh` — серия измерений при загруженном модуле;
- `read_stats.sh` — чтение статистики из `/proc/nf_tcp_lab_stats`;
- `disable_offloads.sh` — отключение offload-механизмов сетевого интерфейса;
- `cleanup.sh` — выгрузка модуля и очистка состояния стенда.

## Требования

Для воспроизведения эксперимента необходимы:

- Linux с поддержкой сборки внешних модулей ядра;
- заголовки и средства сборки для текущей версии ядра;
- `gcc`, `make`;
- `iperf3`;
- права `root` для загрузки и выгрузки модуля;
- два Linux-узла в изолированном сегменте сети.

## Сборка модуля

В каталоге проекта выполните:

```bash
make
```

При необходимости можно предварительно очистить артефакты сборки:

```bash
make clean
make
```

## Подготовка сетевого интерфейса

Для более корректной оценки программных накладных расходов рекомендуется отключить аппаратные offload-механизмы на клиентском узле:

```bash
sudo ./disable_offloads.sh <iface>
```

Пример:

```bash
sudo ./disable_offloads.sh enp0s8
```

## Запуск сервера

На серверном узле запустите:

```bash
./run_server.sh 5201 logs
```

Здесь `5201` — TCP-порт `iperf3`, а `logs` — каталог для сохранения логов.

## Базовый эксперимент

На клиентском узле выполните серию эталонных измерений без загрузки модуля:

```bash
./run_client_baseline.sh <server_ip> <port> <seconds> <parallel> <runs> <log_dir>
```

Пример:

```bash
./run_client_baseline.sh 10.0.0.2 5201 30 1 5 logs
```

## Эксперимент с пассивным перехватом

Для запуска режима перехвата без активной дополнительной обработки выполните:

```bash
./run_client_hook.sh <server_ip> <iface> <port> <seconds> <parallel> <runs> <log_dir> passive 4
```

Пример:

```bash
./run_client_hook.sh 10.0.0.2 enp0s8 5201 30 1 5 logs passive 4
```

В этом режиме модуль загружается с параметром `enable_transform=0`, а статистика обработки сохраняется после каждого прогона.

## Эксперимент с активной дополнительной обработкой

Для запуска режима активной обработки используйте:

```bash
./run_client_hook.sh <server_ip> <iface> <port> <seconds> <parallel> <runs> <log_dir> active <transform_level>
```

Пример для `transform_level=4`:

```bash
./run_client_hook.sh 10.0.0.2 enp0s8 5201 30 1 5 logs active 4
```

При необходимости можно использовать другие значения параметра `transform_level`, например `8` или `12`.

## Чтение статистики модуля

Текущее состояние статистики можно посмотреть так:

```bash
./read_stats.sh
```

Либо напрямую:

```bash
cat /proc/nf_tcp_lab_stats
```

## Очистка после эксперимента

После завершения измерений модуль можно выгрузить командой:

```bash
sudo rmmod nf_tcp_lab
```

Либо использовать сценарий очистки:

```bash
./cleanup.sh
```

## Интерпретация результатов

Основные метрики исследования:

- пропускная способность TCP-соединения по данным `iperf3`;
- число ретрансляций;
- загрузка процессора на клиентском узле;
- среднее время обработки пакета в hook-функции, публикуемое модулем через `procfs`.

В активном режиме реализована не фактическая модификация TCP-заголовка в проходящем трафике, а вычислительная модель дополнительной обработки пакета. Поэтому результаты следует интерпретировать как оценку влияния внутрядерных накладных расходов на производительность сетевого взаимодействия.

## Примечание

Проект предназначен для использования в учебном и исследовательском изолированном стенде. Перед воспроизведением эксперимента необходимо убедиться, что версия заголовков и средств сборки соответствует текущему загруженному ядру Linux.
